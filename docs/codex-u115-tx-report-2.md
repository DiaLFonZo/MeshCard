# U115 long TX investigation 2: bridge startup and RF path

**Scope and result.** This is a source and binary inspection of the current v4 bridge, both U115 host paths, and the installed CubeCell 1.4.0 reference. No device was flashed; no firmware was built or changed. The earlier report's LDO mismatch was real but was **not the complete cause**: both hosts now select DC-DC, and the reported ADV-to-Zero 84-byte packet succeeded once after two CRC failures while Zero-to-ADV long TX still fails. The available evidence does **not** establish a unique root cause. A static TX FIFO error before SetTx cannot by itself explain a receiver-side LoRa CRC error: the SX1262 normally calculates its CRC over the bytes it actually transmits. The evidence points to an on-air integrity fault or a modem-state fault during TX, but no bridge or hardware root cause is proved.

Paths below are relative to the repository unless prefixed with "CubeCell:", which means C:\Users\enant\AppData\Local\Arduino15\packages\CubeCell\hardware\CubeCell\1.4.0. Line numbers describe the sources inspected on 2026-11-20; the worktree has pre-existing uncommitted edits. The present v4 source is not proof of the contents of the installed v3 hex on the ADV.

## What actually runs before boardInitMcu

- firmware/build.ps1:6-9 selects CubeCell-Module for ASR6501 and wraps both boardInitMcu and cyfitter_cfg. firmware/u115_bridge/u115_bridge.ino:175-188 calls the **real** cyfitter_cfg from its wrapper, restores SWD, and replaces boardInitMcu with bridgeBoardInit.
- CubeCell:cores/asr650x/projects/PSoC4/Cm0plusStart.c:311-346 runs the C runtime and constructors; :491-519 calls cyfitter_cfg. The current bridge ELF confirms that initialize_psoc calls __wrap_cyfitter_cfg at address 0x2ad0 and the real cyfitter_cfg at 0x2224. Disassembly of the latter shows CySysClkWcoStart and CySysClkWriteImoFreq(48), plus peripheral mux/clock register writes. Thus the bridge **does run** the generated clock-tree, IMO, WCO, and pin-mux startup. Neither bridgeBoardInit nor Heltec's boardInitMcu is responsible for that setup.
- tools/patch_direct_boot.py:7-11 copies only eight bytes (app SP/reset vector from 0x2200 to 0x0). The copied vector reaches the ordinary app reset/startup path; it does not remove cyfitter_cfg or the C runtime. firmware/build.ps1:8-14 builds/copies an unpatched hex; direct-boot patching is a separate operation. No evidence here shows that skipping the UART bootloader removes a required radio initialization.
- CubeCell:cores/asr650x/board/src/asr_board.c:334-355 is the actual boardInitMcu: SpiInit, Asr_Timer_Init, RtcInit, systime assignment, a board-variant Vext/VBAT block, SX126xIoInit, delays, SX126xReset, and sx126xSleep. There is **no ASR6501 regulator, radio-supply, RF-switch, crystal-trim, or PA setup in this function**. The Vext block at :340-350 excludes the CubeCell-Module target selected by firmware/build.ps1:6. The SX1262 DC-DC mode is later selected in CubeCell:libraries/LoraWan102/src/radio/radio.c:491-505, and the U115 host now matches it at meshtastic-firmware/src/mesh/SX126xInterface.cpp:140-146.

## Ranked explanations after the DC-DC result

1. **TX-time RF or modem integrity, cause not established.** The symptom is a receiver-side LoRa CRC error after an apparently full-length TX; the intact beginning and frequent tail failure fit a signal or synchronization impairment that develops over airtime. DC-DC's partial improvement is consistent with a power-sensitive effect, but it does not identify a failed rail, switch, oscillator, or PA. The bridge drives P6.1 high and the host enables DIO2 (bridge_board.c:120-124; SX126xInterface.cpp:202-215). Physical levels and RF waveform have not been measured, so no hardware defect is claimed.
2. **A radio configuration command lost or corrupted through the bridge.** The SPI helper's timeout can be silently converted to a normal XFER response (u115_bridge.ino:103-110; CubeCell:cores/asr650x/board/src/spi-board.c:53-77). A bad command could leave a modem or PA register wrong, although the supplied Zero trace already verifies key packet parameters, errata writes, full SetTx airtime, and sparse bus traffic during TX. This is a software path worth instrumenting, but there is no observed failure in it.
3. **Zero-specific staged-buffer handoff or host command sequence.** meshtastic-firmware/src/mesh/SX126xInterface.cpp:803-856,895-925 stages payload before CAD and may change TX buffer base. It merits separate inspection for Zero-to-ADV, but cannot explain ADV-to-Zero alone. Static payload corruption before SetTx would ordinarily produce a valid LoRa CRC on the wrong bytes, so it is a poor explanation for the reported -7.
4. **Bridge reset pulse and release mode.** Bridge's 2-ms low and driven-high idle differ from CubeCell's 40-ms low and hi-z release (bridge_board.c:52-57; CubeCell:cores/asr650x/board/src/asr_board.c:80-89). A marginal reset could leave stale chip state, but working long RX and occasional long TX success make it a weak fit.
5. **SPI divider, skipped RTC/timer/sleep, WFE, SWD, direct boot.** These are real implementation differences with little causal support for receiver CRC after an autonomous full-length TX. Nominal SPI divider is zero in both. The v3/v4 sleep comparison already weakens CPU activity as a cause.

## Proposed fix and single test

**No evidence-based code fix can yet be identified.** The bridge already selects the expected P6.1 strong-high state, and the host requests the expected DIO2 RF-switch mode. Changing either blindly could degrade RX as well as TX. A prudent bridge hardening patch is to reject a 0xFFFF SpiInOut timeout and report an explicit SPI error instead of returning an apparently successful XFER; this closes a real error-handling defect, but **it is not a demonstrated fix for these CRC failures**. Matching CubeCell's 40-ms reset low and releasing RESET to hi-z is another controlled software experiment, not an established remedy. Neither requires lowering 22 dBm or changing LongFast.

**One discriminating test at 22 dBm:** on both U115s, correlate each fixed 84-byte LongFast send's success/CRC failure with a synchronized recording from SetTx through TX_DONE of (a) the physical P6.1 pin and antenna-switch VDD, (b) DIO2 at the switch control input, and (c) RF output envelope and carrier frequency against a short-packet baseline; log bridge SPI timeout and command-status failures in the same run. Keep the receiver and all modem settings fixed. If P6.1 or DIO2 changes unexpectedly only on failed long sends, correct the bridge/host control path responsible and repeat the **same** run to verify all three signals and CRC reception. If those pins stay correct but RF envelope/frequency degrades during failed long sends, the measurement supports a TX analog/power/clock investigation; do not label a specific hardware part without its measured voltage/frequency evidence. If RF remains stable while CRC fails, compare the actual SX1262 modem/PA registers and an independent on-air decode. A pre-SetTx FIFO readback can be added as a secondary transport diagnostic, but a match or mismatch there alone cannot prove the CRC cause.
